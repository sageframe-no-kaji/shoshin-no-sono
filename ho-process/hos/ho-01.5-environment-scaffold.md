# ho-01.5 — Environment scaffold

ho-00 produced the repo, the schema, and the framing documents. ho-01 produced the data. Neither produced a *technical* scaffold — there is no page to serve, no test harness, no lint stack, no project CLAUDE.md. ho-02 is the first code ho and inherits that gap directly: its done-means ("browser console on the preview URL," "hot-reloadable module") has nothing to stand on. This ho is the forward-only response — an inserted ho, not a reopening of ho-00. It encodes the verification discipline into the repo so that every code ho after it finds the standard already in place.

**Out of scope:** Any Indexer code (ho-02). Any rendering or UI beyond the placeholder page (ho-03+). The GitHub Action deploy pipeline to sageframe-dharma (a later ho; the System Design's build pipeline ships when there's something to ship). Cloudflare Pages configuration — deferred by practitioner call until the MVP catalog needs a shareable URL (the ho-03 era); local serving suffices through ho-02. Sveltia/admin anything (ho-10+).

## Phase 1 — Think

### Decision 1 — The site stays no-build; dev tooling lives in devDependencies only.

The System Design commits to vanilla HTML/JS/CSS with native ES modules and d3-force via ESM CDN. This ho honors that strictly: the *served* site is the source — no bundler, no transpile, no build artifacts. Everything this ho adds (Vitest, TypeScript-as-checker, ESLint, Prettier) is development tooling in `devDependencies`, invisible to the deployed page. `node_modules/` is gitignored; Cloudflare Pages serves the repo checkout directly with no build command. Why: the no-build property is an architectural commitment from the seed onward, and the cheapest way to keep it honest is to make the deploy path incapable of depending on a build.

### Decision 2 — Layout: `index.html` at root, `src/` for modules, `tests/` for specs, `scripts/` for repo tooling.

```
index.html              ← the page (placeholder now; the catalog later)
src/                    ← ESM modules (ho-02: indexer.js; later: gate.js, cartographer.js)
tests/                  ← Vitest specs
scripts/                ← repo tooling (validate-works.mjs)
works.json, schema.json ← stay at root; the page fetches /works.json
```

Why: `works.json` at root keeps the fetch path stable and the Steward/Founder edit target unambiguous. `src/` mirrors the practitioner's Python habit (production code in one place, tests in another) translated to this stack. `scripts/` holds tooling that is *about* the repo rather than *of* the site — the validator is not shipped.

### Decision 3 — Test harness: Vitest, coverage thresholds at 90%.

Ratified by the practitioner. ESM-native, zero-config at this repo shape, built-in v8 coverage. Coverage thresholds set to 90% (lines/branches/functions) in the Vitest config per the operating discipline's floor — enforced from the first code ho, not retrofitted. Why Vitest over `node --test`: built-in coverage and watch mode without flag archaeology; the cost (a devDependency tree) never touches the served site.

### Decision 4 — Type layer: JSDoc annotations checked by `tsc --noEmit` in strict mode.

Ratified by the practitioner. `tsconfig.json` with `allowJs + checkJs + strict + noEmit` — the shipped `.js` files are the source of truth, annotated with JSDoc; TypeScript runs purely as a checker. Why: the discipline treats type checking as a load-bearing verification layer, and the first three code hos (Indexer, Gate, grid) are exactly where data-shape errors live. JSDoc-over-`.ts` keeps the no-build commitment: nothing needs compiling to run.

### Decision 5 — Lint and format: ESLint (flat config) + Prettier.

ESLint for correctness-class lint (unused vars, unreachable code, accidental globals), Prettier for formatting so format never becomes a conversation. Why this pair: it is the ruff-equivalent for this stack — boring, dominant, well-understood by any agent that reads the repo. Config stays minimal; rules tighten only when a real failure motivates it.

### Decision 6 — The works.json validator is promoted into the repo: `scripts/validate-works.mjs`.

Ratified by the practitioner. During ho-01 the structural checks (required fields, controlled vocabularies, strength rules, theme limits, referential integrity of `target` and `articulated_in`, group-number contiguity) ran as ephemeral throwaways. This ho encodes them as a committed script with a non-zero exit on failure. Why now: `schema.json` is a *descriptive* contract (prose-annotated, not a strict JSON Schema document), so off-the-shelf validators can't enforce it — the checks have to live somewhere, and three downstream consumers need them (pre-commit, the future GitHub Action, the Steward's edit loop). Plain Node, no dependencies, so it runs anywhere including CI.

### Decision 7 — Pre-commit enforcement via the `pre-commit` framework, hooks running npm scripts.

`.pre-commit-config.yaml` with local hooks: `npm run validate`, `npm run lint`, `npm run typecheck`, `npm test`. Why the Python `pre-commit` tool in a JS repo: it is the practitioner's established hook manager across all projects, it is language-agnostic by design, and using it keeps the encoded environment consistent — an agent reading any Sageframe repo finds the verification stack declared in the same file in the same place. Husky would add a JS-ecosystem dependency to do the same job less consistently.

### Decision 8 — Project CLAUDE.md is written here, project-specific, with no language-module import.

The `~/.claude/modules/languages-web.md` module encodes the Eleventy and HTMX+Jinja2 patterns — neither applies to a no-build vanilla-ESM site, so importing it would mislead the agent. The project CLAUDE.md instead carries its own conventions: the component boundary rules from the System Design (the Indexer is the only component that knows the on-disk data shape; the Garden Gate is the only component that touches the URL; the Cartographer is a pure render component), the no-build commitment, the verification commands, the repo layout, the branch discipline (work on `labs`), and pointers into the Kamae chain and ho-process. Why: the encoded environment is the instruction — ho-02's agent should find these rules in the repo, not in conversation.

### Decision 9 — The placeholder page doubles as the verification surface.

`index.html` carries the identity block from the System Design (初心の園 / Shoshin no Sono / the tagline) and nothing else visual — but it loads `src/main.js` as a module, which (from ho-02 onward) fetches `works.json` and exposes the Indexer on `window` for console verification. Why: the overview's ho-02 done-means says "browser console *on the preview URL*" — making the placeholder the console surface means no throwaway debug page, and the preview URL becomes meaningful one ho earlier.

### Deferred — Cloudflare Pages preview.

Practitioner call at authoring: not yet. Local serving covers everything this ho and ho-02 verify; a shareable URL first matters when the MVP catalog exists (ho-03). Pages configuration (project connected to `sageframe-no-kaji/shoshin-no-sono`, no build command, output directory `/`, `labs` as preview branch) lands then. ho-00's preview-URL claim stays unconfirmed; nothing depends on it until ho-03.

## Phase 2 — Execute

Single bounded agent conversation in Claude Code, practitioner monitoring. No agent-task decomposition — the work is one seam.

Sequence: `package.json` + devDependencies → `tsconfig.json`, ESLint, Prettier configs → Vitest config with coverage thresholds → `scripts/validate-works.mjs` (port the ho-01 checks; verify it passes against current works.json and *fails* against a deliberately broken copy) → smoke test in `tests/` so the suite runs green → `.pre-commit-config.yaml` wired to the npm scripts → `index.html` placeholder + empty `src/main.js` → `.gitignore` additions (`node_modules/`, `coverage/`) → `CLAUDE.md` → commit(s) on `labs`.

### Done means

- `npm test` runs green (smoke test) with coverage reporting wired at 90% thresholds
- `npm run validate` passes against `works.json` and exits non-zero against a corrupted fixture
- `npm run typecheck` (tsc strict) and `npm run lint` both clean
- `pre-commit run --all-files` executes the full stack
- `index.html` serves locally via any static server and renders the identity block
- `CLAUDE.md` at repo root carries the component boundaries, conventions, and verification commands
- All committed on `labs` with the scaffold as identifiable commits
